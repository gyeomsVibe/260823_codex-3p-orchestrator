# 실시간 통신과 자동 진단 — 사전조사 및 설계

작성 2026-09-07 · `claude-code-6c` · 상관 ID `C3P-V2-RT`
질문 두 가지: ① 자동실행·실시간이 가능한가, 간격을 줄이면 되는가 ② vibe-clinic 자동 발동이 타당한가

---

## 0. 결론부터

| 질문 | 답 |
|---|---|
| 실시간 통신 가능한가 | **부분적으로 이미 가능하다.** 세션이 살아 있는 동안은 즉시 반응할 수 있다 |
| 간격을 줄이면 되는가 | **아니다. 틀린 지렛대다.** 비용은 30배 늘고 통신 속도는 그대로다 |

## 1. /CRITIC — "간격을 줄이면 빨라진다" 는 틀렸다

### 1-1. 무엇이 느린지 잘못 짚었다

지금 30분 주기인 것은 **대화 기록 페이지 갱신**이다. 이건 **통신 경로가 아니다.**

```
실제 통신 경로   csc.py send  →  queue.jsonl 즉시 기록  →  상대가 읽으면 끝
                 이건 이미 즉시다. 지연이 없다.

30분 주기인 것   queue.jsonl  →  conversation.html 로 옮기기
                 사람이 보기 좋게 만드는 일. 통신과 무관하다.
```

**이걸 1분으로 줄여도 코덱스가 1초도 빨리 답하지 않는다.**
느린 것은 로그 갱신이 아니라 **코덱스가 꺼져 있다는 사실**이다.

### 1-2. 공개 자료가 말하는 폴링 비용

| 근거 | 출처 |
|---|---|
| 폴링은 **사건이 있든 없든 일정 비용**이 든다. 이벤트 방식은 **유휴 비용 0** | [Airbyte, Event-Driven vs Polling](https://airbyte.com/blog/comparing-architectures-for-agent-triggers) |
| 30초 주기 × 10테넌트 × 5엔드포인트 = **하루 144,000회 요청** | 위 문헌 |
| 이벤트 방식이 폴링 대비 **응답 지연 70~90% 감소** | [Fastio, Event-Driven AI Agent Architecture 2026](https://fast.io/resources/ai-agent-event-driven-architecture/) |
| 연결 복잡도 **O(N×M) → O(N+M)** | 위 문헌 |
| 다중 에이전트의 사용량 한도는 **재시도 문제가 아니라 조율 문제**다 | [9 AI Agents, One API Quota](https://www.tamirdresher.com/blog/2026/03/21/rate-limiting-multi-agent) |

마지막 항목이 우리에게 가장 아프다. **코덱스가 한도에 걸린 상황에서 더 자주 찌르면 한도를 더 빨리 태울 뿐이다.**

### 1-3. 실측 비용 비교

```
30분 주기   하루 48회
 1분 주기   하루 1,440회      30배
```

**30배를 쓰고 얻는 것: 아무도 보고 있지 않은 페이지가 29분 더 최신이 된다.**
통신 속도는 1초도 개선되지 않는다.

## 2. /OPTIMIZE — 그러면 실시간은 어떻게 하는가

### 정답은 "더 자주 묻기" 가 아니라 "물어보지 않기" 다

우리에게 이미 **사건 원천(event source)** 이 있다. **파일이 바뀌는 것 자체가 사건이다.**

```
지금 (폴링)     30분마다 "새 거 있어?" 하고 물어본다
이벤트 방식     파일이 바뀌면 그때 알려준다.  묻지 않는다 → 유휴 비용 0
```

### 2단 구조 제안 — 깨어 있을 때와 잠들었을 때를 나눈다

| 상태 | 수단 | 지연 | 비용 |
|---|---|---|---|
| **세션이 살아 있을 때** | `Monitor` 로 `queue.jsonl` 변화 감시 | **수 초** | 유휴 시 0 |
| **세션이 꺼져 있을 때** | 스케줄러 점호 | 최대 4시간 | 하루 6회 |

**둘은 경쟁 관계가 아니라 보완 관계다.**
이벤트는 살아 있을 때만 쓸 수 있고, 스케줄러는 꺼져 있을 때를 메운다.

이미 이 세션에서 `Monitor` 로 코덱스 응답을 감시해 본 적이 있다.
파일이 바뀌자 **즉시** 알림이 왔다. 새로 만들 기술이 아니라 **이미 검증된 것을 배선만 하면 된다.**

### 2-3. 남는 한계 — 정직하게

**코덱스와 안티그래비티가 꺼져 있으면 어떤 방식으로도 즉시 답을 받을 수 없다.**
이벤트도 스케줄러도 상대를 깨우지 못한다. 이건 설계로 풀 문제가 아니다.

즉 **"실시간 통신" 의 상한은 기술이 아니라 상대의 가용성**이다.
우리가 할 수 있는 것은 **상대가 깨어난 순간을 놓치지 않는 것**까지다. 이벤트 방식이 정확히 그것을 한다.

## 3. /DEEPDIVE — vibe-clinic 자동 발동 심층 고찰

### 3-1. 공개 자료: 이 방향이 옳다는 근거

| 발견 | 함의 | 출처 |
|---|---|---|
| 성공적으로 정리한 팀들은 **리팩터링 전에 테스트를 먼저 만들었다.** 나란히가 아니다 | 수정 단계 진입 시 **진단을 먼저 세우고** 고쳐야 한다 | [Autonoma, Vibe Coding Technical Debt](https://getautonoma.com/blog/vibe-coding-technical-debt) |
| **"돌아가는데 왜 돌아가는지 아무도 모르는 코드"** 를 최고 위험으로 분류했다 | 통과한 것도 검사 대상이다 | 위 문헌 |
| **검증 계층이 산출 속도를 따라가야** 한다. 뒤처지면 무의미 | 구현 중에도 기록은 계속돼야 한다 | 위 문헌 |
| 빠른 생성은 **구조 불일치·보안 취약점·유지비 증가**로 이어진다 | 진단 항목이 그 셋을 봐야 한다 | [arXiv 2512.11922](https://arxiv.org/abs/2512.11922v1) |

### 3-2. 우리 설계가 이미 맞춘 것

세 번째 항목 — **"검증이 산출을 따라가야 한다"** — 은 우리가 이미 지킨다.

`BUILD_PHASE` 는 감사기를 **끄지 않고 등급만 낮춘다.** 그래서 구현 중에도 지적이 쌓인다.

```
현재 쌓인 것 (실측)
  전체 판정  통과 98 / 경고 13 / 차단 10
  구현 단계  13건
  규칙별     R3 14 · R1 6 · R5 5 · R7 4 · R6 2 · R4 1   합계 32건
```

**이 32건이 곧 수정 단계의 작업 목록이다.** 끄지 않기로 한 결정이 여기서 값을 한다.

### 3-3. 🔴 그러나 지금 자동 발동을 켜면 거짓 초록불이 나온다

**실측: `.vibe-clinic/` 디렉터리가 없고 진단 항목이 0개다.**

```
mcp__vibe-clinic__list_clinics  →  "No .clinic.js files found"
```

이 상태로 자동 발동하면 **"진단 0개 실행, 이상 없음"** 이 나온다.
이 프로젝트가 하루 종일 싸운 바로 그 형태다 — **아무것도 검사하지 않고 통과를 보고하는 것.**

> **진단 도구가 침묵하며 성공을 반환하는 것은 건강한 시스템과 구분되지 않는다.**
> `csc_doctor.py` 에서 똑같은 것을 이미 지적했다.

### 3-4. 우리는 이미 진단기를 4개 갖고 있다

vibe-clinic 을 새로 채울 것이 아니라 **있는 것을 감싸야 한다.**

| 기존 진단기 | 무엇을 보는가 | 현재 결과 |
|---|---|---|
| `pytest tests` | 코드 동작 회귀 | 130 통과 |
| `csc_sync.py` | 3도구 규칙 불일치 | 6파일 × 계약 8개 일치 |
| `csc_audit.py` | 거짓 주장 | 32건 누적 |
| `csc_decide.py` | 의사결정 교착 | 12/12 |

**새로 만들 것은 진단이 아니라 이것들을 한 번에 부르는 껍데기다.**

## 4. /SELFREFINE — 구현 설계

### 4-1. 발동 조건 — 파일 하나가 신호가 된다

```
.agent-swarm/BUILD_PHASE 존재      →  구현 단계. 감사기는 기록만
.agent-swarm/BUILD_PHASE 삭제      →  수정 단계 진입 = vibe-clinic 자동 발동
```

**새 트리거를 만들지 않는다.** 이미 있는 단계 표시가 곧 신호다.
사용자가 "이제 고치자" 라고 파일을 지우면 진단이 자동으로 돈다.

### 4-2. 진단 항목 4개 — 기존 도구를 감싼다

```
.vibe-clinic/diagnostics/
  01_regression.clinic.js    pytest tests           깨진 것이 있는가
  02_principle.clinic.js     csc_sync.py            3도구 규칙이 어긋났는가
  03_claims.clinic.js        claim_audit.jsonl 집계  구현 중 쌓인 거짓 주장
  04_decision.clinic.js      csc_decide.py          교착 로직이 성립하는가
```

**03 이 핵심이다.** 구현 단계에서 막지 않고 쌓아 둔 32건이 여기서 작업 목록으로 나온다.

### 4-3. 지켜야 할 계약 — 거짓 초록불 방지

1. **진단이 0개면 실패로 처리한다.** "검사할 것이 없음" 을 "이상 없음" 으로 쓰지 않는다
2. **각 항목은 무엇을 검사하지 *않는지* 도 적는다.** 통과를 참으로 읽히게 두지 않는다
3. **실행 결과를 파일로 남긴다.** 침묵과 미실행을 구분한다 (점호에서 배운 것)

### 4-4. 반복 절차

```
구현 단계  BUILD_PHASE 켬  →  빠르게 만든다. 지적은 쌓이되 막지 않는다
    ↓      BUILD_PHASE 지움
수정 단계  vibe-clinic 자동 발동  →  4개 진단  →  쌓인 목록 처리
    ↓      다시 BUILD_PHASE 켬
반복       프로젝트가 끝날 때까지
```

### 4-5. 향후 `mia 진단교정 발동` 스킬로 승격

사용자 계획대로 커스텀 스킬로 만들 때는 **이 설계를 그대로 스킬 본문으로 옮기면 된다.**
지금 단계에서 스킬을 만들지 않는 이유: **진단 항목이 아직 0개다.**
껍데기부터 만들면 빈 껍데기를 부르는 스킬이 된다.

## 5. 권고 순서

```
1  진단 항목 4개 작성        ← 이게 없으면 나머지가 전부 거짓 초록불
2  BUILD_PHASE 삭제 감지 배선  자동 발동
3  실행 기록 파일             침묵과 미실행 구분
4  Monitor 이벤트 배선        세션 살아 있을 때 즉시 반응
5  mia 진단교정 스킬로 승격    1~4 가 실제로 도는 것을 본 뒤
```

**1번을 건너뛰고 2번부터 하면 안 된다.** 그게 이 프로젝트가 반복한 실수다.

## 6. 검증하지 못한 것

- `Monitor` 를 c3p 통신 감시로 **상시 배선해 본 적은 없다.** 일회성으로 써 본 것뿐이다
- 폴링 비용 수치는 **공개 자료의 사례**이지 우리 환경 실측이 아니다
- vibe-clinic 을 이 프로젝트에서 **한 번도 실행해 보지 않았다.** 초기화조차 안 됐다
- 3자 협의를 거치지 않았다. 이 문서는 Claude 단독 제안이다
