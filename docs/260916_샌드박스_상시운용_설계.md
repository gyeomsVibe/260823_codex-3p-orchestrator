# 샌드박스 상시 운용 설계 — 주기 점검과 git 작업 경로

- 작성: 2026-09-16
- 목표: Codex 샌드박스를 항상 켜 둔 채로, 권한 거부 때문에 작업이 막히지 않게 한다
- 설정: `sandbox_mode = "workspace-write"`, `approval_policy = "never"`, `[windows] sandbox = "elevated"`

---

## 1. 샌드박스는 실제로 작동하는가 — 실측

샌드박스 안에서 경계를 직접 찔러 본 결과다.

| 시험 | 결과 |
|---|---|
| 실행 계정(`whoami`) | `desktop-73uopo2\codexsandboxoffline` — 사용자 계정이 아님 |
| 사용자 홈 폴더 쓰기 | **거부** |
| `C:\Windows\Temp` 쓰기 | **거부** |
| 작업 폴더 쓰기 | 허용 |
| 네트워크 접근 | **거부** (숨겨진 소켓 오류) |
| `.git` 폴더 쓰기 | **거부** |

샌드박스는 전용 계정으로 실행되며 파일·네트워크 경계를 모두 강제한다. 세션 지시문에도 `approval_policy`가 `never`이므로 권한 상승 요청을 쓰지 말라고 명시돼 있다. 즉 **거부를 우회하는 경로는 열려 있지 않다.**

---

## 2. 거부의 정체

`.git` 거부는 특정 **샌드박스 계정 SID를 대상으로 한 거부(DENY) 권한**이다. 샌드박스가 git 이력을 보호하려고 심는데, 종료할 때 지우지 않아 계속 남는다.

- 대상 계정은 `CodexSandboxOffline`이다. 이 계정은 고정이므로, 한 번 거부가 걸리면 이후 실행이 계속 막힌다.
- 실행 1회마다 저장소당 2~3건이 추가된다. 작업 폴더 전체를 훑었더니 저장소 16곳에서 39건(거부 26건)이 나왔다.
- 계정이 교체되며 삭제되면 이름이 풀리지 않는 고아 SID로 남는다. 이 상태에서는 `icacls /remove`가 오류 1332로 실패한다. 그래서 SID를 직접 다뤄야 한다.

### 시간대별 실측 (같은 날)

| 시각 | 상태 | git 결과 |
|---|---|---|
| 15:19 | 정리 작업이 거부 항목 39건 제거 | — |
| 15:23~15:27 | 거부 항목 없음 | 커밋 3회 **성공**, 잠금 실패 0건 |
| 17:03~17:06 | 샌드박스가 거부 항목 재생성 | `index.lock: Permission denied` 18건, 커밋 **실패** |

**결론: 정리는 다음 샌드박스 실행까지만 유효한 임시 해소다.** 근본 해결이 아니다.

## 3. 운용 설계

### 1계층 — 자동 청소 (구현 완료)

작업 폴더의 Git 저장소를 자동으로 찾아 찌꺼기 권한을 지운다. 새 저장소를 만들어도 등록할 필요가 없다.

| 구성 요소 | 내용 |
|---|---|
| 점검·정리기 | `tools/codex-sandbox-acl.ps1` (`-Mode Check` / `-Mode Clean`) |
| 스케줄러 실행기 | `tools/codex-sandbox-acl-task.ps1` (저장소 자동 탐색, 깊이 2단계) |
| 예약 작업 | `CodexSandboxAclCleanup`, 30분 간격 |
| 로그 | `%LOCALAPPDATA%\codex-sandbox-acl.log` — 실행마다 한 줄 |

이 계층의 목적은 **권한 항목의 무한 누적을 막는 것**이다. git 거부를 영구히 없애지는 못한다.

### 2계층 — git 쓰기 전용 경로 (권장)

커밋·푸시는 `gitops` 프로필로 한다. 이 프로필은 샌드박스를 쓰지 않으므로 거부 항목과 무관하게 항상 성공한다.

파일 위치는 `~/.codex/gitops.config.toml`이다. Codex가 프로필 형식을 바꿔서, `config.toml` 안의 `[profiles.*]`는 옛 형식이며 남아 있으면 `--profile` 사용 자체가 막힌다.

```
sandbox_mode = "danger-full-access"
```

```
codex --profile gitops
```

**대가:** 이 프로필에서는 샌드박스 보호가 없다. git 작업에만 쓰고, 일반 작업은 기본 프로필로 한다.

### 3계층 — 상태 감시

로그 한 줄의 형식은 다음과 같다.

```
2026-09-16 15:19:27 mode=Clean targets=32 stale=39 deny=26
```

- `stale` 값이 계속 커지면 청소 주기를 줄인다.
- `mode=Check`에서 `stale`이 0이 아니면 종료 코드 1이 나오므로 다른 점검 도구에 물리기 쉽다.
- 수동 점검: `pwsh -NoProfile -File tools\codex-sandbox-acl.ps1`
- 예약 작업은 `tools/codex-sandbox-acl-task.cmd`를 호출한다. 이 래퍼가 표준 출력과 오류를 `%LOCALAPPDATA%\codex-sandbox-acl-task.out`에 남긴다.
- **로그가 비어 보일 수 있다.** 앱 컨테이너(MSIX) 안에서 실행하는 도구는 `%LOCALAPPDATA%` 쓰기가 패키지 폴더로 리디렉션된다. 같은 이름의 사본이 두 곳에 생기므로, 동작 확인은 로그 대신 권한 상태로 한다.

## 4. 현재 적용 상태

| 항목 | 값 |
|---|---|
| 기본 샌드박스 | `workspace-write` (상시) |
| 승인 정책 | `never` (사용자 설정 유지) |
| git 전용 프로필 | `~/.codex/gitops.config.toml` (전체 접근) |
| 예약 작업 | `CodexSandboxAclCleanup` 30분 간격, 상태 Ready |
| 마지막 청소 | 저장소 16곳, 찌꺼기 39건 제거 |

## 5. 운용 메모

- **비대화형 실행은 설정을 무시한다.** `codex exec`는 전체 접근으로 돌므로 `--sandbox workspace-write`를 직접 줘야 한다.
- **거부가 나면 순서대로 확인한다.** ① `.git` 쓰기면 정상 동작이다. `gitops` 프로필로 처리한다. ② 작업 폴더 밖이면 정상 동작이다. ③ 그 외면 점검 스크립트를 돌린다.
- **네트워크가 필요한 작업**(`git fetch`, 패키지 설치)도 기본 샌드박스에서는 막힌다.
- **소유자가 바뀌는 증상**은 이 스크립트로 못 고친다. 관리자 권한에서 `takeown`으로 소유권을 되찾아야 한다.
- **예약 작업 해제**: `schtasks /Delete /TN CodexSandboxAclCleanup /F`

## 6. 검증 기록

| 시험 | 조건 | 결과 |
|---|---|---|
| 경계 확인 | `--sandbox workspace-write` | 계정·파일·네트워크 경계 모두 강제됨 |
| 커밋 A·A2 | 청소 직후, 샌드박스 | 성공 (거부 항목이 없던 구간) |
| 커밋 B | `--profile gitops` | 성공 |
| 커밋·fetch 재시험 | 거부 항목 재생성 후, 샌드박스 | 실패 (`index.lock`, `FETCH_HEAD` 거부) |
| 스케줄러 검증 | 가짜 거부 항목을 심고 예약 작업 실행 | 제거 확인 — 자동 정리 정상 동작 |

앞선 초안에는 "샌드박스에서는 커밋이 항상 거부된다"와 "청소하면 해결된다"가 섞여 있었다. 둘 다 부정확해 위 실측으로 바로잡았다.
