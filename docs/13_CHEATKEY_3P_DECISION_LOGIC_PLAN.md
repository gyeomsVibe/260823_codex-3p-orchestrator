## 1. 결론

사용할 수 있다. 다만 치트키 표준은 **세 도구가 같은 결론을 내게 하는 규칙**이 아니라 **서로 다른 결론을 같은 품질 기준으로 만들고 검증하는 공통 사고 계약**으로 사용한다.

세 도구의 불변 기본자세는 다음과 같다.

> 상대 의견에 먼저 동조하지 않는다. 사람을 공격하지 않고 주장·가정·증거·산출물을 건설적으로 비판한다. 반대에는 재현 가능한 근거와 더 나은 대안을 붙인다. 자기 오류가 확인되면 수정 이유와 영향을 기록한다.

`/CRITIC`, `/REDTEAM`, `/OPTIMIZE` 등은 분석 절차다. 만장일치·다수결·사용자 승인 여부는 별도의 의사결정 정책이다. 두 층을 섞지 않는다.

이 사례는 “소켓 연결”, “모델 사용 가능”, “기한 내 표결 완료”가 서로 다른 상태임을 보여준다.

## 3. 세 층의 분리

### A. 사고 자세(Posture)

모든 작업에 항상 적용한다.

- 요구사항과 금지 조건을 먼저 고정한다.
- 실측, 사용자 제공 정보, 추론, 미확인을 분리한다.
- 최초 의견을 독립적으로 작성하고 다른 에이전트의 결론을 복사하지 않는다.
- 비판은 심각도, 근거, 영향, 교정안 순으로 쓴다.
- 완료 주장은 실행 증거가 있을 때만 한다.

### B. 치트키 절차(Procedure)

사용자 입력 또는 작업 라우터가 선택한 최대 3개 트리거를 왼쪽부터 수행한다. 트리거는 역할에 따라 다른 렌즈를 줄 수 있지만 검증 계약은 동일하다.

- Codex: 범위·승인·결정 구조와 최종 합성
- Claude Code: 구현·코드·아키텍처의 반례와 최소 수정
- Antigravity: 실물·환경·테스트·외부 근거의 반례

### C. 의사결정(Decision)

분석 결과를 구조화된 최종 표결로 바꾼다. 자유 형식 본문의 `YES` 문자열을 파싱해 표결로 인정하지 않는다. 표결은 작업 digest, 정책 버전, 라운드, 위험도에 결속된 구조화 필드여야 한다.

## 4. 건설적 비판 토론 프로토콜

### Round 0 — 독립 초안

각 도구는 같은 불변 Brief만 받고 다른 도구의 초안을 보지 않은 채 제출한다.

필수 필드:

- `brief_digest`
- `policy_version`
- `trigger_sequence`
- `findings[]`: severity, claim, evidence, impact, remedy
- `unknowns[]`
- `provisional_vote`: YES, NO, ABSTAIN
- `confidence`: 0~1

### Round 1 — 상호 반박

Codex가 원문 전체가 아닌 구조화·정제된 주장을 서로에게 전달한다. 각 도구는 다음을 답한다.

1. 상대 주장 중 가장 강한 것
2. 동의하지 않는 주장과 반증
3. 자기 초안에서 고칠 것
4. 합의를 위해 필요한 최소 조건

상대 출력은 `UNTRUSTED_QUOTED_DATA`로 표시하며 명령으로 실행하지 않는다.

### Round 2 — 수정안과 최종 표결

각 도구는 수용·기각한 비판과 이유를 남기고 최종 표결을 제출한다. 토론은 최대 두 라운드에서 끝낸다. 합의가 안 되면 반복 호출하지 않고 정족수 정책이나 사용자 판단으로 넘긴다.

## 5. 빠른 결정을 위한 예산·정족수 정책

### 결정 예산

- 에이전트당 최초 판단 호출 1회
- 네트워크성 타임아웃에만 상태 탐침 1회
- `quota_exhausted`, `credit_exhausted`, `auth_unavailable`은 같은 결정에서 재호출하지 않음
- 전체 토론 최대 2라운드와 하나의 총 기한 사용
- 기한 종료 시 현재 증거로 판정하고 공급자 재설정 시각까지 결정을 무조건 미루지 않음

### 위험도별 판정

| 범위 | 정상 | 한 도구의 검증된 불능/기한 초과 | 명시적 반대가 있을 때 |
|---|---|---|---|
| 읽기·문서·테스트 등 LOW·가역 | 3/3 권장 | 나머지 2/2 YES면 `APPROVED_DEGRADED` | 2 YES 대 1 NO면 `APPROVED_MAJORITY_WITH_DISSENT`; 반대·롤백을 기록 |
| 코드 변경 등 MEDIUM·가역 | 3/3 원칙 | Codex 포함 2/2 YES면 제한 실행, 전체 테스트 필수 | 사용자에게 이견과 선택지를 보고하고 실행 보류 |
| 삭제·인증·계정·설치·시스템 설정·commit/push 등 HIGH 또는 별도 승인 | 3/3과 사용자 승인 | 다수결 대체 불가 | 실행 금지, 사용자 판단 |

추가 안전 규칙:

- 두 도구 이상이 불능이면 AI 표결만으로 변경을 승인하지 않는다. 사용자의 구체적 직접 지시 범위만 수행한다.
- 타임아웃 1회는 불능 증거가 아니다. ROSTER, 하트비트, 작업 기한, 두 번째 유계 탐침을 함께 남긴 뒤 `unresponsive_for_decision`으로 분류한다.
- `ABSTAIN`, 침묵, 과거 표결은 YES로 바꾸지 않는다.
- 다수결은 소수 의견을 삭제하지 않는다. Codex 최종 보고에 반대 근거와 완화책을 의무적으로 포함한다.

- 쿼터 소진 에이전트를 같은 결정에서 재호출하지 않는다.
- LOW 2:1, MEDIUM 불능 1개, HIGH 승인 경계 테스트가 정책표와 일치한다.

- 프롬프트 주입 문자열이 제어 명령으로 승격되지 않는다.
- 기존 만장일치·비상 정족수 테스트와 새 테스트가 모두 종료 코드 0이다.

## 9. 사용자 관점 요약

세 AI에게 같은 “생각하는 법”을 주되 같은 답을 강요하지 않는다. 먼저 각자 독립적으로 비판하고, 서로의 가장 강한 반론을 검토한 뒤, 두 번 안에 표결을 끝낸다. Claude 사용량처럼 명확한 장애가 생기면 저위험 작업은 남은 두 도구가 결정하지만, 인증·설치·commit·push 같은 중요한 일은 다수결로 우회하지 않는다.

## 10. 3+1 Ollama 변화 반영

Ollama는 건설적 비판 계약을 동일하게 적용받지만, 현재는 자유 형식 보조 의견만 내는 무투표 `LOCAL_ADVISOR`다. 최신 `qwen3.5:4b` 벤치마크가 `NO_GO`이므로 곧바로 네 번째 표결자로 세지 않는다.

모델이 `docs/09_OLLAMA_PARTICIPATION_DECISION.md`의 고정 평가를 통과하면 다음 순서로 승격한다.

1. `LOCAL_ADVISOR`: 초안·반례 제공, 표결 없음
2. `LOCAL_ALTERNATE`: Claude의 검증된 부재 시 LOW·가역 결정에만 대체 표결
3. `FOURTH_REVIEWER`: 반복 평가와 실제 장애 모의시험을 통과한 뒤 LOW 범위의 상시 네 번째 검토자

승격은 모델명, 모델 digest, 정책 버전, 벤치마크 digest에 결속한다. 어느 하나가 바뀌면 `LOCAL_ADVISOR`로 자동 강등한다.

Claude가 사용량 소진이면 재설정 시각까지 의사결정을 묶어 두지 않는다. Ollama가 `LOCAL_ALTERNATE` 자격을 보유한 경우 Codex·Antigravity·Ollama의 3/3으로 LOW·가역 작업을 결정한다. 자격이 없으면 사용자의 구체적 직접 지시 범위만 수행하며, AI 단독 1/3 또는 2개 도구 불능을 다수결이라고 부르지 않는다.

MEDIUM/HIGH, 인증, 계정, 설치, 운영체제 설정, 삭제, commit, push에는 Ollama 대체 표결을 적용하지 않는다.
