실시간으로 만들 수 있나? 진단을 자동으로 돌릴 수 있나?

보고서 05 · 2026년 9월 7일 · 작성 Claude Code · 조사 단계
두 질문에 대한 답을 먼저 드립니다. ① 실시간은 이미 부분적으로 가능합니다. 다만 주기를 짧게 하는 건 틀린 방법입니다 — 비용만 30배 늘고 통신은 1초도 안 빨라집니다.
② 자동 진단은 방향이 맞습니다. 다만 지금 켜면 "0개 검사하고 이상 없음"이 나옵니다.

1. 첫 번째 질문 — 주기를 짧게 하면 빨라지나요?

🔴 제가 먼저 짚어야 할 것: 느린 게 뭔지 잘못 보셨습니다

지금 30분마다 도는 것은 "대화 기록 페이지를 새로 만드는 일"입니다. 이건 도구끼리 말을 주고받는 통로가 아닙니다.

지금 얼마나 걸리나
실제 통신 — 메시지를 보내고 파일에 기록즉시. 지연이 없습니다
30분 주기인 것 — 그 기록을 보기 좋은 페이지로 옮기기30분

이걸 1분으로 줄여도 Codex가 1초도 빨리 답하지 않습니다.
느린 것은 페이지 갱신이 아니라 Codex가 꺼져 있다는 사실입니다.

비용은 이렇게 늘어납니다

30분 주기   하루    48회
 1분 주기   하루 1,440회      ← 30배

30배를 쓰고 얻는 것: 아무도 보고 있지 않은 페이지가 29분 더 최신이 됩니다. 통신 속도는 그대로입니다.

공개 자료가 말하는 것

발견뜻
주기적으로 물어보는 방식은 일이 있든 없든 비용이 든다. 사건이 생길 때만 알리는 방식은 놀고 있을 때 비용이 0안 물어보는 게 싸다
사건 방식이 응답 지연 70~90% 감소빠르기까지 하다
여러 AI의 사용량 한도 문제는 재시도 문제가 아니라 조율 문제 더 자주 찌르면 한도만 빨리 태운다

출처: Airbyte · Fastio 2026 · 9 AI Agents, One API Quota

2. 그러면 실시간은 어떻게 하나요

정답은 "더 자주 물어보기"가 아니라 "안 물어보기"입니다.

지금       30분마다 "새 거 있어?" 하고 물어본다
바꾸면     파일이 바뀌면 그때 알려준다  →  안 물어보니 놀 때 비용 0

우리에겐 이미 사건이 생기는 자리가 있습니다. 파일이 바뀌는 것 자체가 사건입니다.

깨어 있을 때와 잠들었을 때를 나눕니다

상태방법얼마나 빠른가비용
세션이 살아 있을 때파일 변화를 지켜봄몇 초놀 때 0
세션이 꺼져 있을 때스케줄러 점호최대 4시간하루 6회

둘은 경쟁이 아니라 보완입니다. 사건 방식은 살아 있을 때만 쓸 수 있고, 스케줄러는 꺼져 있는 동안을 메웁니다.

이 방식은 이미 이 세션에서 써 봤습니다. Codex 응답을 지켜보게 해뒀더니 파일이 바뀌자 즉시 알림이 왔습니다. 새로 만들 기술이 아니라 연결만 하면 됩니다.

🔴 그래도 남는 한계 — 정직하게

Codex와 Antigravity가 꺼져 있으면 어떤 방법으로도 즉시 답을 받을 수 없습니다. 사건 방식도 스케줄러도 상대를 깨우지는 못합니다.

즉 "실시간"의 한계는 기술이 아니라 상대가 켜져 있느냐입니다. 우리가 할 수 있는 건 상대가 깨어난 순간을 놓치지 않는 것까지입니다.

3. 두 번째 질문 — 진단을 자동으로 돌리는 게 맞나요

방향은 맞습니다. 공개 자료가 뒷받침합니다.

발견우리에게 주는 뜻
빠르게 만든 코드를 성공적으로 정리한 팀들은 고치기 전에 검사 도구를 먼저 세웠다수정 단계에 들어갈 때 진단부터 돌리는 게 맞다
"돌아가는데 왜 돌아가는지 아무도 모르는 코드"를 가장 위험하게 봤다 통과한 것도 검사 대상이다
검사가 만드는 속도를 따라가야 한다. 뒤처지면 의미 없다 만드는 중에도 기록은 계속돼야 한다

출처: Vibe Coding Technical Debt · arXiv 2512.11922

세 번째 항목은 이미 지키고 있습니다.

지난번에 "거짓 잡는 장치를 끄지 않고 등급만 낮추자"고 한 이유가 이것입니다. 만드는 동안에도 지적이 계속 쌓입니다.

지금까지 쌓인 것 (실제로 센 숫자)
  전체 판정   통과 98 · 경고 13 · 차단 10
  규칙별 지적  32건

끄지 않기로 한 결정 덕에 이 기록이 남았습니다.

🔴 정정 — 이 32건을 "할 일 목록"이라 쓴 것은 틀렸습니다

보고서를 낸 뒤 실제로 열어봤더니 제가 성격을 잘못 말했습니다.

내용
제가 쓴 것"이 32건이 곧 수정 단계의 할 일 목록"
실제32건 전부가 최소 10.9시간 전 것, 대부분 28~41시간 전.
최근 24시간 안에 생긴 것은 1건뿐이고, 그것도 Codex가 8분 만에 스스로 고쳤습니다.

그리고 "없다"던 파일들은 지금 다 있습니다. 그때 지적이 옳았고, 그래서 이미 고쳐진 것입니다.

이건 열려 있는 결함 목록이 아니라 과거에 한 말의 장부입니다. 이미 보낸 메시지는 되돌릴 수 없습니다. 장부의 숫자를 "할 일"이라 부르면 안 됩니다.

숫자를 크게 말한 게 아니라 성격을 잘못 말했습니다.

그래서 진단기를 고쳤습니다

누적만 세면 이 숫자는 영원히 늘기만 합니다. 32 → 40 → 60. 그러면 사람은 곧 이 항목을 안 읽게 되고, 진짜 문제가 생겨도 지나칩니다.

최근 24시간 것   →  지금 고칠 목록
그보다 오래된 것  →  "이미 지난 일이며 할 일 목록이 아닙니다" 라고 명시

지금 출력은 "최근 1건 · 오래된 기록 31건"입니다. 숫자가 다시 뜻을 갖게 됐습니다.

4. 🔴 그런데 지금 켜면 안 됩니다

실제로 확인해봤습니다. 진단 항목이 0개입니다.

진단 목록 조회  →  "No .clinic.js files found"
설치 폴더       →  없음

이 상태로 자동 발동하면 나오는 결과는:

"진단 0개 실행, 이상 없음"

아무것도 검사하지 않고 통과를 보고하는 것 — 오늘 하루 종일 싸운 바로 그 형태입니다.

바로 어제 다른 도구에서 똑같은 걸 지적했습니다: "진단 도구가 침묵하며 성공을 반환하는 것은 건강한 시스템과 구분되지 않는다."

다행히 검사기는 이미 4개 있습니다

새로 만들 게 아니라 있는 걸 한 번에 부르게 묶으면 됩니다.

이미 있는 검사기무엇을 보나지금 결과
동작 검사고치다 깨진 게 있나130개 통과
규칙 동기화세 도구 규칙이 어긋났나6파일 일치
거짓 주장 감사지어낸 말이 있었나최근 1건 · 지난 기록 31건
1건은 Codex가 자체 해소
결정 로직결정이 멈추지 않나12/12

5. 어떻게 만들 것인가

발동 신호 — 새로 만들지 않습니다

BUILD_PHASE 파일이 있다   →  만드는 중. 지적은 쌓이되 막지 않음
BUILD_PHASE 파일을 지운다  →  고치는 단계 진입 = 진단 자동 발동

이미 있는 표시가 곧 신호가 됩니다. "이제 고치자" 하고 파일을 지우면 진단이 알아서 돕니다.

반복 절차

만드는 단계  →  빠르게 구현, 지적은 쌓임
      ↓ (파일 지움)
고치는 단계  →  진단 자동 발동, 쌓인 목록 처리
      ↓ (파일 다시 만듦)
반복        →  프로젝트가 끝날 때까지

반드시 지킬 것 — 거짓 초록불 방지

1진단이 0개면 실패로 처리합니다. "검사할 게 없음"을 "이상 없음"으로 쓰지 않습니다
2각 항목이 무엇을 검사하지 않는지도 적습니다
3실행 기록을 파일로 남깁니다. 침묵과 미실행을 구분하기 위해서입니다

6. 권고 순서

할 일왜 이 순서인가
1진단 항목 4개 먼저 만들기 이게 없으면 나머지가 전부 거짓 초록불
2파일 삭제 감지해서 자동 발동 연결
3실행 기록 남기기침묵과 미실행 구분
4파일 변화 감시 연결 (실시간)살아 있을 때 즉시 반응
5mia 진단교정 발동 스킬로 승격1~4가 실제로 도는 걸 본 뒤

1번을 건너뛰고 2번부터 하면 안 됩니다. 껍데기부터 만들면 빈 껍데기를 부르는 스킬이 됩니다. 그게 이 프로젝트가 반복한 실수입니다.

7. 아직 확인하지 못한 것

파일 변화 감시를 상시로 연결해 본 적이 없습니다. 한 번 써 본 것뿐입니다
비용 수치는 공개 자료의 사례이지 우리 환경에서 잰 게 아닙니다
vibe-clinic을 이 프로젝트에서 한 번도 실행해 본 적이 없습니다. 설치조차 안 됐습니다
세 도구 협의를 거치지 않았습니다. Claude 혼자 만든 제안입니다

8. 정해주실 것

1번(진단 항목 4개 만들기)부터 진행할까요?

이건 되돌릴 수 있고 승인이 필요 없지만, 지금 방향이 맞는지 먼저 확인받고 싶습니다. 특히 "주기를 짧게 하는 건 틀린 방법"이라는 제 판단에 동의하시는지가 중요합니다 — 동의하지 않으시면 설계 전체가 달라집니다.

기술 상세는 docs/26_REALTIME_AND_AUTO_CLINIC_DESIGN.md에 있습니다.

이 보고서에서 쓴 숫자는 전부 실제로 센 것입니다. 진단 항목 0개는 조회해서 확인했고, 지적 건수는 기록 파일을 세었습니다.
처음에 "32건 = 할 일 목록"이라고 쓴 것은 성격을 잘못 말한 것이라 위에서 정정했습니다. 공개 자료 수치는 출처를 함께 적었으며 우리 환경에서 잰 값이 아닙니다.

아직 아무것도 바꾸지 않았습니다. 조사와 설계 단계입니다.
