새 협업 방식을 실제로 켰습니다

보고서 04 · 2026년 9월 7일 · 작성 Claude Code
승인해 주신 대로 4단계를 모두 실행했습니다. 자동 실행 장치 2개가 등록됐고, 항상 켜둘 프로그램은 0개가 됐으며, 감시 화면 만들기를 멈췄습니다. 검사 130개가 모두 통과했습니다.

1. 무엇을 켰나 — 스케줄러 2개

스케줄러(scheduler, 정해진 시각에 자동으로 실행해 주는 장치) 두 개를 등록했습니다. 사람이 시키지 않아도 알아서 돕니다.

이름언제하는 일드는 비용
대화 기록 갱신 30분마다
매시 7분·37분 예정
+ 최대 10분 지연		 세 도구가 주고받은 말을 읽기 좋은 페이지로 옮김 0
AI를 안 부름
점호 4시간마다
2·6·10·14·18·22시 23분 예정
+ 약간 지연		 안 읽은 메시지를 확인하고 답할 게 있으면 한 줄 남김 적음

왜 30분·4시간인가 — 사람이 볼 때 최신이면 충분하기 때문입니다. 아무도 안 보는 페이지를 1초마다 다시 그릴 이유가 없습니다.

왜 7분·37분처럼 어중간한 시각인가 — 전 세계 사용자가 모두 정각을 고르면 같은 순간에 몰립니다. 몇 분 비켜두면 그 혼잡을 피합니다.

가장 큰 변화: 지금까지는 대화가 하나도 없어도 프로그램 3개가 계속 돌았습니다. 이제는 일이 있을 때만 비용이 듭니다.

2. "발동" 이라고 칠 필요가 없어졌습니다

지금까지는 매번 c3p 발동이라고 입력해야 협업이 시작됐습니다. 이제 도구를 켜는 순간 자동으로 합류합니다.

Claude Code에는 시작 훅(SessionStart hook, 프로그램이 켜질 때 자동으로 실행되는 짧은 명령)이 있습니다. 그 출력이 그대로 AI가 읽는 내용이 됩니다. 그래서 그 자리에 협업 상태를 넣었습니다.

[c3p 자동 합류] 협의체 통신이 켜졌다. 별도 발동 문구는 필요 없다.

🔴 만들자마자 제가 낸 오류를 하나 잡았습니다

처음 만든 것은 켤 때마다 "막힌 안건 3건"이라고 알렸습니다. 실제로는 0건입니다.

원인: 과거에 "막혔다"고 적힌 옛날 기록까지 세고 있었습니다. "지금 막혀 있음"과 "한때 막혔었음"을 구분하지 못했습니다.

왜 중요한가:

거짓 초록불만 위험한 게 아닙니다. 거짓 빨간불도 똑같이 위험합니다.
켤 때마다 없는 경고가 뜨면 사람은 곧 그 경고를 읽지 않게 됩니다. 그러면 진짜로 막혔을 때도 지나칩니다. 경보의 신뢰를 태워 없애는 셈입니다.

판단 기준을 규약 문서의 표 한 곳으로 모았습니다. 같은 값을 두 곳에서 다르게 세면 어느 쪽을 믿을지 알 수 없기 때문입니다. 이 프로젝트는 그 실수를 이미 두 번 했습니다.

3. 낭비를 실제로 줄였습니다

기록을 새로 만드는 데 1.3초가 걸립니다. 그런데 이걸 세 군데서 불렀습니다.

부르던 자리얼마나 자주바꾼 뒤
사용자가 말할 때마다매 대화뺐습니다
명령을 실행할 때마다한 세션에 수백 번뺐습니다
도구를 켤 때한 번남겼습니다

아무도 보고 있지 않은 페이지를 수백 번 다시 그리고 있었습니다.

그리고 지시하신 대로 감시 화면 만들기를 멈췄습니다. 파일과 코드는 지우지 않았습니다 — 만들기만 멈췄습니다. 판단이 바뀌면 한 줄만 되돌리면 됩니다.

4. "먼저 만들고 나중에 고친다"를 켰습니다

지시하신 대로 주장 감사기(claim auditor, 거짓 주장을 자동으로 잡아내는 장치)가 더 이상 발신을 막지 않습니다.

다만 끄지 않고 등급만 낮췄습니다.

끄면등급만 낮추면 (선택)
속도빠름똑같이 빠름
기록아무것도 안 남음지적이 그대로 쌓임
나중에뭘 고칠지 모름쌓인 목록이 곧 할 일

"나중에 고친다"의 '나중에'가 성립하려면 무엇을 고칠지 알아야 합니다. 고칠 목록 없이 고칠 수는 없습니다.

켜졌는지는 파일 하나로 눈에 보이게 했습니다. .agent-swarm/BUILD_PHASE가 있으면 켜진 상태고, 지우면 즉시 원래대로 돌아갑니다. 숨은 설정으로 하지 않은 이유는 켜졌는지 사람이 확인할 수 있어야 하기 때문입니다.

5. 용어 쓰는 방식을 바꿨습니다

말씀하신 대로 전문용어에 쉬운 설명을 반드시 붙이도록 규칙을 고쳤습니다.

예시
전스케줄러(scheduler)
후스케줄러(scheduler, 정해진 시각에 자동으로 실행해 주는 장치)

영어를 붙였다고 설명한 것이 아닙니다. scheduler를 모르는 사람에게 스케줄러(scheduler)는 모르는 말이 두 번 나온 것과 같습니다. 뜻은 세 번째에만 있습니다.

이 규칙을 6개 규칙 파일 전부에 넣었고, 검사 도구가 하나라도 빠지면 알려주도록 했습니다.

7. 첫 실행 결과 — 그리고 제가 틀리게 적었던 것

✅ 스케줄러가 실제로 돌았습니다

증거값
스케줄러가 기록한 실행 시각18:46:50
대화 기록 파일이 실제로 바뀐 시각18:46:53
차이3초 — 두 증거가 일치합니다

서로 다른 두 곳에서 같은 답이 나왔습니다. 스케줄러가 "돌았다"고 말한 것과, 파일이 실제로 바뀐 것이 3초 안에 맞물립니다.

🔴 그런데 제가 시각을 틀리게 적었습니다

내용
제가 적은 것"매시 7분·37분에 실행"
실제18시 46분 50초에 실행
차이의 정체9분 40초 — 스케줄러가 일부러 넣는 지연

37분 + 9분 40초 = 46분 50초. 정확히 맞아떨어집니다.

지터(jitter, 일부러 조금씩 어긋나게 넣는 지연)라고 부릅니다. 전 세계 사용자가 모두 같은 순간에 몰리는 것을 막으려고 스케줄러가 알아서 넣습니다.

제 잘못은 예정 시각을 확정 시각처럼 적은 것입니다. "7분·37분에 실행된다"고 쓰면, 46분에 도는 것을 본 사람은 고장 났다고 생각합니다. 멀쩡한데 고장으로 오해하게 만드는 설명은 틀린 설명입니다.

위 표를 "예정 + 최대 10분 지연"으로 고쳤습니다.

점호는 아직 돌지 않았습니다

4시간마다라서 다음 차례가 22시 23분입니다. 아직 한 번도 실행되지 않았습니다. "등록됐다"와 "돌았다"는 다르므로 그대로 적습니다.

🔴 점호에 있던 결함 하나를 미리 고쳤습니다

점호는 "할 말이 없으면 아무것도 남기지 않는다"고 만들었습니다. 그런데 그러면

돌았는데 할 말이 없었다   →  침묵
아예 돌지 않았다          →  침묵

두 가지가 똑같이 보입니다. 구분할 수 없으면 고장 나도 모릅니다.

고친 방법: 할 말이 없어도 "도착했다"와 "끝났다"만은 항상 기록하게 했습니다. 시작만 있고 끝이 없으면 중간에 멈춘 것이고, 그 자체가 진단 정보가 됩니다.
