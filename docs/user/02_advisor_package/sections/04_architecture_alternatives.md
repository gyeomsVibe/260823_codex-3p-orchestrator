# ⚖️ 제4절: 향후 아키텍처 대안 3종 비교

| 구분 | 대안 A. 순수 Ephemeral 스케줄러 (교수님 원안) | 대안 B. 상주 소켓 브로커 + 데몬 (현재 본선) | 대안 C. 하이브리드 모델 (권고안) |
|---|---|---|---|
| **핵심 구조** | 스케줄러가 매번 `subprocess.run`으로 CLI 단발 호출, SQLite에만 기록 | 127.0.0.1 TCP 소켓 서버 상주, 세 도구 워커가 TCP 상시 연결 | 상태/결정은 SQLite+스케줄러가 주도하되, 실시간 알림/대시보드 푸시만 경량 소켓 사용 |
| **핵심 장점** | 세션 소실, 동기화 락, 좀비 프로세스 문제가 100% 소멸. 가장 단순하고 견고함 | 초고속 메시지 중계 (지연시간 < 5ms). 에이전트 간 즉각적 핑퐁 토론 가능 | 스케줄러의 결정론적 검증력과 실시간 사용자 UI/감시판 반응성을 동시 확보 |
| **핵심 단점** | 매 턴마다 CLI 기동 오버헤드 (5~10초 소요). 도구 간 연속 토론 시 지연 큼 | Windows 프로세스/파일 잠금 문제 취약. 브로커 생존 관리(Liveness) 오버헤드 큼 | 두 메커니즘을 함께 유지해야 하므로 코드 복잡도가 다소 증가함 |
| **추천도** | ⭐⭐⭐⭐ (안정성 최상) | ⭐⭐ (운영 리스크 존재) | ⭐⭐⭐⭐⭐ (실용성 최상) |
