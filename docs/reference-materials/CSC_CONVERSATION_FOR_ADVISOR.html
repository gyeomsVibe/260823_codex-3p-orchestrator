  * 서브프로세스에 파일 쓰기 제한을 걸더라도, CLI 도구가 원격 API를 호출하기 위해서는 사용자 환경의 자격 증명(API Token, OAuth 세션, `~/.gemini`, `~/.claude.json` 등)을 필연적으로 읽을 수 있어야 합니다.
  * 대상 코드베이스나 외부 입력에 **간접 프롬프트 인젝션(Indirect Prompt Injection)**이 포함되어 있을 경우, 읽기 권한을 악용해 세션 토큰이나 개인정보를 추론 결과(stdout/stderr)에 노출하도록 유도할 수 있습니다.
  * 이렇게 유출된 시크릿이 영속 폴백 버스인 **JSONL 로그에 평문으로 영구 기록**되어, 로컬 디스크 상의 광범위한 보안 침해로 확산됩니다.

### ③ Ollama `qwen3.5:4b`의 콜드 스타트 지연과 효용성 역전 (Cold-Start Latency & Utility Paradox)
* **결함 메커니즘**:
  * 제시된 제약 조건(`keep_alive=0`, 비투표권, 툴/파일/시크릿 접근 불가, 동시성 1) 하에서 `qwen3.5:4b`는 매 호출마다 모델 가중치를 VRAM/RAM에 로드하고 해제하는 **콜드 스타트 I/O 오버헤드(최소 2~5초)**를 발생시킵니다.
  * 이 모델은 비투표(Non-voting)에 파일/도구 접근권이 없으므로 단순 문법 검증이나 스키마 분류 외에는 수행할 수 있는 역할이 없습니다. 그러나 4B급 경량 모델은 복잡한 JSON Schema 제약(Structured Outputs)을 원샷으로 완벽하게 만족하지 못해 빈번한 재생성(Retry)을 유발합니다.
  * 결과적으로 상위 클라우드 CLI의 할당량(Quota) 소진 시 실질적인 코딩 대행이나 폴백 역할을 전혀 수행하지 못하면서, 로컬 시스템의 I/O와 메모리만 낭비하는 **데드 웨이트(Dead Weight)**가 됩니다.

## 3. 심층 잔여 위험 식별 (Identified Remaining Risks)

개정안이 훌륭하게 정제되었으나, Windows 환경 및 실제 런타임 구현 시 반드시 방어해야 하는 **6대 잔여 위험**이 존재합니다.

### ⚠️ 위험 1. Windows 프로세스 트리 고아화 위험 (Process-Tree Orphan Hazard)
- **현상**: Windows에서는 부모 프로세스(CLI 래퍼)가 타임아웃이나 예외로 강제 종료(`taskkill` / `SIGTERM`)되어도, 하위 자식·손자 프로세스(`node.exe`, `git.exe`, `python.exe` 등)가 백그라운드에 남아 포트나 파일을 잠그는 고질적 문제가 발생합니다.
- **방어책**: 단순 PID kill에 의존하지 않고 Windows API의 **Job Object(`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`)**를 바인딩하여 부모 종료 시 자식 프로세스 트리가 커널 레벨에서 원자적(Atomic)으로 일괄 수거되도록 강제해야 합니다.

### ⚠️ 위험 2. 루프백 브로커의 IPC 무인증 노출 (Loopback IPC Attack Surface)
- **현상**: 브로커가 로컬 포트(`127.0.0.1`)에 바인딩되어 있더라도, 동일 머신에서 실행되는 악성 스크립트나 브라우저 기반의 로컬 포트 스캔/CSRF 요청이 브로커 API를 호출할 가능성이 있습니다.
- **방어책**: 브로커 실행 시 메모리에 1회용 고엔트로피 인증 토큰(`Bearer Token`)을 생성하고, 하위 어댑터 및 Codex 호출 시 헤더 검증(`X-3P-Token`)을 필수로 요구해야 합니다.

### ⚠️ 위험 3. `stdin DEVNULL` 환경에서 CLI 즉각 크래시 (EOF Exception Trap)
- **현상**: 대화형(Interactive) 셸을 기본값으로 전제하는 CLI 도구(예: Claude Code, 일반 LLM CLI)는 `stdin`이 `DEVNULL`로 닫혀 있으면 입력을 기다리지 못하고 즉시 `EOFError` 또는 비정상 종료(Exit Code 1)를 일으킵니다.
- **방어책**: CLI 호출 명령문에 비대화형 플래그(예: `-p`, `--print`, `--non-interactive`, `--no-confirm`)를 반드시 결합하고, TTY 요구 바이너리의 경우 유사 파이프 예외 처리를 검증해야 합니다.

### ⚠️ 위험 4. 스트리밍 청크 경계의 시크릿 마스킹 누수 (Chunk-Boundary Leak)
- **현상**: 정규표현식 기반 출력 마스킹(`secret redaction`)을 실시간 스트리밍에 적용할 때, 시크릿 문자열(예: `sk-ant-api03...`)이 패킷 경계에서 두 청크로 쪼개져 전달되면 정규식 매칭을 우회하여 브로커 로그에 평문 노출될 수 있습니다.
- **방어책**: 슬라이딩 윈도우 버퍼(Sliding Window Buffer)를 적용하거나, 태스크 완료 후 통합 출력 버퍼 단위로 2차 전수 마스킹을 거친 후 저장·전송해야 합니다.

### ⚠️ 위험 5. Ollama의 비의도적 자동 다운로드 및 VRAM 스터터링 (Auto-Pull & VRAM Jitter)
- **현상**:
  1. 로컬에 `qwen3.5:4b` 태그가 정확히 일치하지 않을 경우(예: 실제 로컬 모델명이 `qwen2.5:3b`이거나 태그 오타 시), Ollama 엔드포인트가 외부 저장소에서 수 GB의 가중치를 자동 다운로드(Auto-pull)하여 샌드박스를 위반할 수 있습니다.
  2. 4B 모델 로드/인프런스 순간 GPU VRAM이 급증하여 PC의 다른 GUI/IDE에 일시적 렌더링 끊김(Jitter)이 발생할 수 있습니다.
- **방어책**: 벤치마크 실행 전 `ollama list` 출력을 문자열 대조하여 모델 존재를 반드시 사전 검증하고, 불일치 시 네트워크 요청 없이 즉시 실행을 중단(Fail-Fast)해야 합니다.

### ⚠️ 위험 6. 4B 소형 모델의 JSON Schema 파싱 불안정성 (Markdown Wrap & Malformed JSON)
- **현상**: 4B급 경량 로컬 모델은 엄격한 JSON 스키마를 요구하더라도 응답 앞뒤에 마크다운 블록(```json ... ```)을 붙이거나 말단 쉼표(Trailing comma), 불완전한 괄호 닫기를 출력하는 빈도가 높습니다.
- **방어책**: 벤치마크 평가 시 단순 `json.loads` 실패를 무조건 지능 실패로 볼 것인지, 스키마 준수율과 마크다운 래핑 필터링을 분리 측정할 것인지 채점 기준을 사전에 확립해야 합니다.

## 2. 근본적 물리 한계 및 전제 검증 (Root Verification)

### [검증 1] MCP의 본질적 한계: Host-Client/Server 수명주기 vs Peer-to-Peer Chat
1. **토폴로지 불일치 (Topology Mismatch)**:
   - MCP는 **1개 호스트(Host)가 N개 서버(Server)에 도구/자원을 단방향으로 요청(Request-Response)**하는 클라이언트-서버 프로토콜입니다.
   - 서버는 호스트에게 역방향으로 "지금 새로운 메시지가 도착했으니 추론 턴을 시작하라"고 강제할 수 없습니다. (알림 기능은 수동적 힌트일 뿐, 비동기 턴 기동 트리거가 아님)
2. **`stdio` 전송 계층의 1:1 프로세스 종속성**:
   - `stdio` 기반 MCP 서버는 부모 프로세스가 실행한 파이프(stdin/stdout)에 1:1로 물리 결합됩니다.
   - Claude Code가 MCP 클라이언트로 동작하여 로컬 브리지를 `stdio`로 물고 있으면, Antigravity나 Codex는 그 동일한 `stdio` 스트림에 접근할 수 없습니다. 이를 억지로 풀기 위해 다중 연결용 HTTP/SSE 브리지를 MCP 규격 위에 얹는 것은 표준을 왜곡하는 심각한 오버엔지니어링입니다.

### [검증 2] Codex 앱의 기동 제약: 외부 프로세스의 임의 기동(Wake-up) 불가능성
1. **인바운드 IPC 부재**:
   - OpenAI Codex PC 앱은 사용자 인터랙션 중심의 데스크톱 GUI 애플리케이션이며, 외부 데몬이 임의로 프롬프트를 밀어 넣어 백그라운드 추론을 시작하게 만드는 공식 로컬 리스닝 API(Inbound Webhook/Socket)를 제공하지 않습니다.
2. **사령부(Brain) 모델의 허구성과 실질적 해법**:
   - Codex가 평상시에 가만히 대기하다가 Claude나 Antigravity가 보낸 비동기 TCP 이벤트를 브로커로부터 수신하여 "스스로 깨어나(Wake-up) 판정 보고서를 작성"하는 시나리오는 OS 레벨에서 실현 불가능합니다. (Win32 API나 키보드 이벤트 주입 같은 매크로 방식은 극도로 취약하며 업무용으로 배포 불가능)
   - **유일하게 검증된 정상 해법**: Codex가 사령관으로서 작업을 지시할 때, 백그라운드 완료를 무작정 기다리는 것이 아니라 **Codex 스스로 `python csc.py dispatch --wait` 형태의 단일 CLI 도구를 호출하여 동기식 블로킹(Blocking) 상태로 결과 집계를 대기**해야 합니다. 도구의 표준 출력(stdout)으로 3자 합의 결과가 반환되는 순간 Codex의 다음 턴이 자연스럽게 열립니다.

### [검증 3] 현재 CSC 베이스라인의 취약점: per-TASK 프로세스 스폰과 런타임 보안 공백
1. **per-TASK Bounded CLI Child Process의 병목과 세션 단절**:
   - 작업마다 `claude -p ...` 또는 `agy run ...`을 스폰하면 매번 Node.js/Python 런타임 로딩, Git 저장소 인덱싱, 설정 파일 파싱 등 2~5초의 고정 레이턴시(Cold Start Overhead)가 발생합니다.
   - 프로세스가 종료되면 이전 턴에서 에이전트가 탐색했던 메모리 내 캐시(Context/Hot State)가 전부 소멸하므로, 매번 전체 컨텍스트를 프롬프트에 다시 밀어 넣어야 해 토큰 낭비와 레이턴시 폭증을 부릅니다.
2. **HMAC 코어 분리와 런타임 인증 미통합의 위험성**:
   - HMAC 알고리즘 함수가 존재하더라도 실제 TCP 소켓 핸드셰이크에 인증이 걸려있지 않다면, 로컬호스트(`127.0.0.1`)의 임의의 프로세스나 브라우저의 악의적 웹페이지(DNS Rebinding/Local Port Scanning)가 열려 있는 포트에 접속해 악의적 `TASK_DISPATCH`나 위조된 `RESULT_PUSH`를 주입할 수 있습니다. 이는 로컬 임의 명령 실행(RCE) 위험으로 직결됩니다.

## 3. 안건별 심층 비판 (Detailed Agenda Critique)

### (A) 현재 Adapter 유지 (Keep Current Adapter)
*구조: CSC TCP 브로커 + 영속 Python 어댑터 + per-TASK Bounded CLI 자식 프로세스 + Append-only JSONL*

- **가치 (Value) — [보통]**:
  - 이미 코드가 존재하여 단기적으로 기능 시연(PoC)이 가능하고, 언어에 구애받지 않는 소켓 통신과 감사 로그(JSONL)를 확보함.
- **실현가능성 (Feasibility) — [높음]**:
  - 기존 파이프라인의 연장이므로 추가 개념 설계 없이 바로 구동 가능.
- **지속가능성 (Viability) — [낮음]**:
  - 멀티 턴(Multi-turn) 반복 상호작용 시 프로세스 기동 오버헤드로 인해 실시간 협업 체감이 불가능함.
  - 타임아웃이나 강제 중단 시 자식 프로세스가 고아(Orphan/Zombie)로 남아 파일 락(Lock)을 점유하는 위험이 빈번함.
- **위험 (Risk) — [높음]**:
  - 런타임 인증 미비로 인한 로컬 네트워크 스푸핑 취약점.
  - CLI 호출 시마다 세션이 증발하여 에이전트 간 연속 대화 실패.
- **병목 / 보안 / 세션 한계**:
  - **병목**: 프로세스 생성/종료 I/O 비용 누적, 거대 JSONL 파싱 비용 선형 증가.
  - **보안**: TCP 평문 통신 및 핸드셰이크 부재로 신뢰 경계(Trust Boundary) 붕괴.
  - **세션 지속성**: 프로세스 수명주기와 태스크 수명주기가 1:1로 결합되어 인메모리 컨텍스트 유지 불가.
- **최종 판정**: **PIVOT** (현재 어댑터의 뼈대는 유지하되, CLI 자식 프로세스 스폰 방식을 상주형 워커 방식으로 즉시 전환해야 함)

### (B) MCP stdio 또는 각 도구 MCP 서버/클라이언트로 통합
*구조: Claude Code Bridge와 Antigravity Bridge를 MCP stdio 또는 도구 전용 MCP 서버/클라이언트로 변환*

- **가치 (Value) — [착시적 낮음]**:
  - 최신 표준(MCP)을 사용한다는 명분은 있으나, 다자간 에이전트 오케스트레이션 문제의 본질을 해결하지 못함.
- **실현가능성 (Feasibility) — [매우 낮음]**:
  - Claude Code와 Antigravity는 주로 MCP '호스트(클라이언트)'로 동작하도록 설계되어 있으며, 자기 자신을 다른 에이전트에게 제어받는 범용 MCP '서버'로 열어주는 공식 수단을 기본 제공하지 않음.
- **지속가능성 (Viability) — [원천 불가]**:
  - **수명주기 불일치**: `stdio` 트랜스포트는 부모-자식 간 단일 파이프이므로 브로커가 중계하는 3자 토폴로지를 구성할 수 없음.
  - **비동기 자율 통신 불가**: MCP는 풀(Pull) 기반 도구 호출 규격이므로, 에이전트 A가 에이전트 B에게 "스스로 판단해서 이 문제를 풀라"는 형태의 자율 푸시(Push) 메시징을 표준 규격 내에서 온전하게 처리할 수 없음.
- **위험 (Risk) — [치명적]**:
  - 프로토콜 왜곡으로 인한 스파게티 브리지 양산. MCP 위에 또 다른 폴링 계층을 얹어야 하므로 복잡도만 기하급수적으로 증가.
- **최종 판정**: **NO-GO** (기각: 도구 호출 표준과 분산 에이전트 통신 버스를 혼동한 구조적 오류)

### (C) 하이브리드 제어 평면 / 데이터 평면 (Hybrid Control/Data Plane)
*구조: 경량 고속 인증 제어 평면(IPC/소켓) + 영속 공유 저장소 기반 데이터 평면(파일/버퍼)*

```
[ Control Plane (제어 평면) : 경량, 초저지연, 동기화 ]
   Codex (Caller: dispatch --wait)
      └──[HMAC Authenticated Local Socket]──► CSC Broker Core (Router & Lock Manager)
                                                   ▲                   ▲
                                                   │ (Event Envelope)  │ (Event Envelope)
                                                   ▼                   ▼
                                            Claude Worker       Antigravity Worker
                                            (Persistent Daemon) (Persistent Daemon)

[ Data Plane (데이터 평면) : 대용량 무병목, 무손실 ]
   - Payload Storage : Local Fast Workspace (D:\... or OS Temp Shared Memory)
   - Audit / Event   : SQLite WAL Mode or Partitioned Append-Only JSONL
   - Artifact Passing: File URIs & Diff Pointers (소켓으로 거대 텍스트 전송 배제)
```

- **가치 (Value) — [매우 높음]**:
  - 통신 지연시간을 10ms 미만으로 단축하고, 수백 KB~MB 단위의 코드베이스/AST/스크린샷 전송 시 소켓 직렬화 병목을 완전히 제거.
- **실현가능성 (Feasibility) — [높음]**:
  - 기존 `csc_broker.py`의 라우팅 구조를 유지하면서 워커 프로세스를 상주형(Daemonized REPL 또는 IPC Wrapper)으로 교체하고 파일 포인터 방식을 도입하면 점진적 구현 가능.
- **지속가능성 (Viability) — [매우 높음]**:
  - 도구의 공식 CLI 변경에 영향받지 않는 안정적인 아키텍처.
  - Codex의 앱 특성(동기식 도구 호출자)과 CLI 에이전트의 특성(상주형 백그라운드 실행)을 있는 그대로 완벽히 수용.
- **위험 (Risk) — [보통]**:
  - 상주형 워커의 생명주기 관리(Supervisor Daemon) 및 비정상 종료 시 자동 재기동(Restart) 로직 구현 필요.
- **세부 해결 구조**:
  1. **제어 평면 (Control-Plane)**:
     - **프로토콜**: 루프백(`127.0.0.1`) 전용 소켓 또는 Windows 로컬 네임드 파이프(`\\.\pipe\csc_*`).
