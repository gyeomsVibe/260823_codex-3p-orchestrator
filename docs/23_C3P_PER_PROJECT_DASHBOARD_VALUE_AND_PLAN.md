# C3P 프로젝트별 대시보드 가치평가와 개선 계획

## 판정

**Go.** C3P가 발동되는 프로젝트마다 그 프로젝트의 상태만 보여주는 감시판이 필요하다. 다만 “발동할 때마다 새 대시보드 파일”이 아니라 **프로젝트당 한 파일**인 `.agent-swarm/dashboard.html`을 발동 시 갱신하는 방식이 적합하다.

**현재 범위는 부분 구현이다.** 이번 변경은 CSC 런타임(`csc.py`, `csc_dashboard.py`)이 있는 프로젝트에서 발동과 감시판 생성을 묶는다. 아직 CSC 파일이 없는 임의의 다른 프로젝트에 런타임을 안전하게 배치하는 이식형 부트스트랩은 없다. 따라서 “모든 프로젝트에서 이미 된다”고 보고하면 안 된다.

현재 구현에는 프로젝트용 감시판 생성기가 있었지만 `python csc.py activate`와 연결되지 않았다. 또한 HTML의 30초 새로고침은 이미 생성된 파일을 다시 여는 동작이며 상태를 재계산하지 않는다. 이를 실시간 대시보드라고 부르면 사용자가 낡은 화면을 현재 상태로 오해할 수 있다.

## 사용자가 겪는 문제

- C3P를 켰어도 감시판이 자동으로 생긴다는 보장이 없었다.
- 여러 프로젝트가 하나의 화면을 공유하면 메시지·실패·승인 상태가 섞일 수 있다.
- 실행마다 새 HTML을 만들면 어느 파일이 현재 화면인지 사용자가 다시 판단해야 한다.
- 발동 실패 때 화면이 없으면 가장 필요한 순간의 원인과 다음 행동을 볼 수 없다.

## 세 가지 대안

| 대안 | 장점 | 맹점 | 판정 |
|---|---|---|---|
| 하나의 전역 대시보드 | 한 화면에서 전체 프로젝트를 볼 수 있다 | 프로젝트 경계·권한·원문 경로가 섞이고 다른 저장소의 상태를 잘못 읽기 쉽다 | 기본값으로 부적합 |
| 프로젝트당 한 대시보드 | 물리 작업공간과 원문 큐가 일치하고 프로젝트 전환 때 맥락이 섞이지 않는다 | 프로젝트가 많으면 전체 조망 화면이 따로 필요할 수 있다 | **기본값으로 채택** |
| 발동 실행마다 새 대시보드 | 실행별 보관이 쉽다 | 낡은 파일이 계속 쌓이고 현재 화면 선택이 어려워진다 | 감사 내역은 원문 이벤트로 보존하고 HTML 증식은 금지 |

## 4대 렌즈 평가

| 기준 | 평가 | 근거 |
|---|---|---|
| 가치성(Value) | 높음 | 사용자가 현재 프로젝트의 작동 여부, 실패 이유, 다음 행동을 한 화면에서 확인한다 |
| 실현 가능성(Feasibility) | 높음 | 기존 `csc_dashboard.py`와 프로젝트별 `.agent-swarm` 구조를 그대로 사용한다 |
| 지속 가능성(Viability) | 높음 | 외부 서비스·패키지·계정 없이 정적 HTML 한 파일만 갱신한다 |
| 위험(Risk) | 중간 | 정적 스냅샷을 실시간 화면으로 오해할 수 있어 재계산 시각과 원문 경로를 명시해야 한다 |

## 공개 자료에서 얻은 설계 기준

- OpenAI Agents SDK는 한 작업 흐름을 trace, 세부 단계를 span으로 기록하고 `workflow_name`, `group_id`, metadata로 흐름을 구분한다. 프로젝트 화면도 최소한 프로젝트와 실행 흐름의 식별자를 분리해야 한다: <https://github.com/openai/openai-agents-python/blob/main/docs/tracing.md>.
- Phoenix는 프로젝트를 서로 다른 애플리케이션·환경·실험의 trace가 섞이지 않게 하는 컨테이너로 정의한다. 프로젝트별 분리는 관측 정보의 기본 경계라는 근거다: <https://arize.com/docs/phoenix/tracing/llm-traces/projects>.
- Langfuse는 한 요청을 trace, 여러 요청이 이어지는 상호작용을 session으로 묶는다. 향후 C3P도 프로젝트 감시판 안에서 발동 실행과 대화 세션을 별도 식별해야 한다: <https://langfuse.com/docs/observability/data-model>.

이 자료의 제품을 그대로 설치하자는 뜻은 아니다. 공통 설계 원칙인 **프로젝트 격리, 실행 단위 식별, 원문 추적 가능성**만 로컬 CSC 구조에 적용한다.

## 이번 최소 개선

1. `csc.py activate`가 성공하면 현재 프로젝트 감시판을 만들고 결과 JSON에 프로젝트명·절대 경로·스냅샷 종류를 반환한다.
2. 런타임 발동이 실패해도 감시판 생성을 시도해 실패 상태를 사용자가 볼 수 있게 한다.
3. 화면 제목에 물리 프로젝트 폴더명을 표시한다.
4. “30초마다 상태가 재계산된다”는 오해를 없애고 실제 상태 재계산 시각을 표시한다.
5. Codex·Claude Code·Antigravity 규칙에 같은 계약을 동시 반영하고 회귀 테스트로 고정한다.

## 다음 단계

### P1 — 지금 구현·검증

- 프로젝트별 단일 스냅샷 생성
- 성공·실패 경로 테스트
- 프로젝트 식별과 갱신 시각 표시
- 전체 회귀 테스트

### P2 — 다음 파일럿

- 대상 프로젝트를 먼저 검사하고 필요한 CSC 파일·규칙·제외 정책만 배치하는 `bootstrap --project-root` 설계를 만든다. 기존 파일 충돌 시 덮어쓰지 않고 중단해야 한다.
- 서로 다른 임시 프로젝트 두 곳에서 큐·워커 메타·감시판 경로가 섞이지 않는지 격리 시험을 한다.
- `activation_id`와 `session_id`를 원문 메시지에 추가해 한 프로젝트 안의 여러 발동을 구분한다.
- 브로커 또는 별도 감시 프로세스가 상태 변경 때 감시판을 재생성하도록 한다.
- 생성 프로세스가 멈추면 화면에 `스냅샷 낡음`을 먼저 표시한다.
- Windows에서 재시작·중복 실행·프로세스 종료 후 잔존 파일을 시험한다.

### P3 — 프로젝트가 여러 개일 때만 검토

- 각 프로젝트 대시보드를 덮어쓰지 않고 링크만 모으는 읽기 전용 상위 인덱스를 검토한다.
- 상위 인덱스는 프로젝트 내부 원문·본문을 복사하지 않고 이름, 상태 요약, 마지막 재계산 시각만 읽는다.

## 수용 기준

- `python csc.py activate` 성공과 실패 경로 모두 `.agent-swarm/dashboard.html` 생성 함수를 호출한다.
- 감시판에 현재 물리 프로젝트명이 보인다.
- 결과 JSON이 감시판 경로를 반환한다.
- 감시판은 자신이 스냅샷임을 밝히고 상태 재계산 시각을 표시한다.
- 세 플랫폼 규칙 파일이 같은 생성 계약을 담는다.
- 전체 테스트와 대시보드 자가검사가 종료 코드 0으로 끝난다.

## 사용자가 할 일

이 저장소에서는 별도 설치나 설정이 필요 없다. C3P를 발동한 뒤 `.agent-swarm/dashboard.html`을 열면 된다. 다른 프로젝트 적용은 P2의 충돌 방지 부트스트랩과 격리 시험을 통과한 뒤 진행한다. 실시간 자동 재계산도 같은 파일럿 뒤 기본값 전환 여부를 판단한다.
