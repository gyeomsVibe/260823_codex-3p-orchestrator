# C3P 사용자부재 모드: Antigravity 중심 감시·유한 토론회 설계계획

> 상태: **설계 제안(DESIGN PROPOSAL)** — 구현·커밋·푸시 미승인  
> 작성일: 2026-09-09  
> 선행 조건: C3P 예산절약 모드가 실제로 `READY`일 때만 자동 토론회를 실행한다.  
> 현재 실측: Antigravity 소켓 미등록으로 `PARTIAL_READY`; 따라서 이 문서는 실행 계획이며 3도구 합의 완료가 아니다.

## 1. 무엇을 만들 것인가

**C3P 사용자부재 모드(User-Absence Mode, 사용자가 자리를 비운 동안 사람의 반복 지시 없이 안전한 범위만 준비하는 모드)**를 만든다.

이 모드는 Codex가 사회자(moderator, 의제를 열고 종료를 판정하는 역할)를 맡고,
Antigravity가 증거 수집·정적 검토·품질 확인을 우선 수행한다. Claude Code는 사용량 한도 또는
가용 상태가 확인된 경우에만 수신 회신을 검토하며, 이 모드가 Claude Code를 능동 호출하지 않는다.

목표는 **끝없는 대화가 아니라 검증 가능한 결과 카드**다. 결과 카드는 반드시 아래 중 하나로 닫힌다.

`DECISION_READY`(근거 있는 다음 결정), `IMPLEMENT_READY`(승인 대기 구현 카드),
`BLOCKED`(원인·증거·대안), `NO_ACTIONABLE_CHANGE`(새 행동 없음).

## 2. 왜 이렇게 설계하는가

AutoGen은 메시지 수·토큰 사용량·시간 제한을 조합한 종료 조건을 제공한다. 무한 대화가 아닌
명시적 종료 조건이 필요한 직접 근거다. [AutoGen 종료 조건](https://microsoft.github.io/autogen/dev/user-guide/agentchat-user-guide/tutorial/termination.html)
OpenAI도 실패 한도와 고위험 행동에서 사람 검토를 권고한다. [OpenAI 에이전트 가이드](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)
또한 대화·도구 호출·인계를 추적해야 사후에 원인을 판단할 수 있다. [OpenAI Agents SDK 추적](https://openai.github.io/openai-agents-js/guides/tracing/)

공개 커뮤니티에서는 서로 검증만 반복하는 에이전트가 토큰을 급격히 소모한다는 운영 경험이 보고된다.
이는 보조 관찰일 뿐 설계의 단독 근거는 아니다. [커뮤니티 사례](https://www.reddit.com/r/AI_Agents/comments/1vuarwo/how_do_you_handle_insane_token_costs_when_letting/)

## 3. 트리거와 상태 전이

### 3.1 정확 호출문

`c3p 사용자부재 모드`, `c3p 사용자부재 모드 발동`, `사용자부재 모드`, `사용자부재 모드 발동`을
정확 일치(공백 정리·ASCII 대소문자 비구분·NFC 정규화)로만 인정한다. 설명 문장에 포함된
`사용자부재 모드`는 발동하지 않는다.

### 3.2 상태 기계

```text
OFF → ARMED → RUNNING → (DECISION_READY | IMPLEMENT_READY | BLOCKED | NO_ACTIONABLE_CHANGE)
                  ↓
                PAUSED
```

- `ARMED`: 예산절약 모드가 켜졌지만 `READY`가 아니거나 의제가 없어 로컬 감시만 수행.
- `RUNNING`: 새 의제와 `READY` 증거가 모두 있을 때만 한 번의 유한 토론회 수행.
- `PAUSED`: 사용자 복귀, P2 영역, 시간/메시지/비용 한도 도달, 가용성 악화.
- 종료 상태는 다음 의제가 들어올 때까지 새 모델 호출을 하지 않는다.

## 4. 유한 토론회 규약

| 순서 | 담당 | 허용 산출물 | 상한 |
|---|---|---|---|
| 1. 의제 카드 | Codex | 목표·완료 기준·읽기/쓰기 범위·검증 명령 | 1개 |
| 2. 증거 카드 | Antigravity | 관찰 사실·원문 경로·반례·위험 | 1회 |
| 3. 비판 판정 | Codex | 채택/수정/차단과 이유 | 1회 |
| 4. 반박 또는 수정 | Antigravity | 새 증거가 있을 때만 | 최대 1회 |
| 5. 결과 카드 | Codex | 위 네 결과 중 하나·다음 행동 | 1개 |

**강제 종료 기준**: 최대 5개 모델 메시지, 15분, 동일 논리 응답 재발, 새 증거 없는 반박,
명시적 `BLOCKED`, 또는 한 번의 객관적 검증 실패다. 쿼터가 `unknown`이면 기존 단일·순차
시도 규칙을 적용한다. 관측되지 않은 쿼터 수치나 절감률을 추정하지 않는다.

## 5. Antigravity 중심의 의미와 권한 경계

Antigravity 중심은 **증거 수집과 품질 검토의 우선 배정**이지 지휘권 이전이 아니다.

- Codex: 의제·종료·사용자 보고·권한 판정. 파일 쓰기는 승인된 작업 카드와 소유 범위가 있을 때만 수행.
- Antigravity: 읽기 전용 조사·정적 검토·검증 설계. 직접 파일 수정, 테스트 실행, 원문 큐 편집은 금지.
- Claude Code: 수신 회신만 검토. 활성 TASK·참조 메시지를 보내지 않는다.
- 로컬 감시자: 모델을 깨우기 위한 반복 대화가 아니라 큐 변화·가용성 변화·대시보드 갱신만 수행.

삭제·설치·시크릿·데이터 파괴·커밋·푸시는 사용자 승인을 기다리는 `PAUSED`로 전환한다.

## 6. 세 대안과 판정

| 대안 | 장점 | 결정적 위험 | 판정 |
|---|---|---|---|
| A. 무제한 순환 토론 | 빨리 대화를 시작 | 토큰 폭주·반복·책임 불명확 | 탈락 |
| B. 순수 수동 감시 | 비용 최소 | 결과물·학습이 생성되지 않음 | 보류 |
| C. 변화 기반 유한 토론회 | 결과 카드·비용 상한·감사 가능 | 상태 기계·테스트가 필요 | **채택** |

## 7. 레드팀 위험과 방어

| 위험 | 재현 조건 | 영향 | 방어 |
|---|---|---|---|
| 무한 토론 | 서로 새 근거 없이 비판 반복 | 쿼터 소진 | 메시지·시간·중복 해시 종료 |
| 가짜 가용성 | worker 파일이 `ready`이나 소켓 미등록 | 존재하지 않는 합의 주장 | `ROSTER`+PID+신선 하트비트가 모두 있어야 `READY` |
| 사용자 부재 중 권한 확대 | 구현/커밋을 토론 결과로 포장 | 무단 변경 | P2 즉시 `PAUSED`, Codex 작업 카드 외 쓰기 금지 |
| 한 도구의 표결 유실 | 같은 본문을 다른 발신자가 제출 | 독립 의견 삭제 | `sender+in_reply_to+correlation_id+본문 해시`로 집계 |
| 보고 폭주 | 의미 없는 heartbeat마다 알림 | 사용자 피로·토큰 낭비 | 상태 변화·위험·결과·승인 필요 때만 보고 |

## 8. 사용자 보고 체계

1. **즉시 보고**: P2 승인 필요, `BLOCKED`, 실제 가용성 악화, 감사 위반.
2. **결과 보고**: 토론회 종료 때만 `무엇/왜/사용자 다음 행동` 3줄과 원문 message ID.
3. **조용한 대기**: 새 증거·상태 변화가 없으면 보고하지 않는다.
4. **원문 분리**: 사용자 화면 요약은 `.agent-swarm/messages/queue.jsonl`의 원문을 바꾸지 않는다.

## 9. 단계별 개발 카드 — Antigravity 위임 계획

| 단계 | 소유자 | 변경 후보 | 완료 기준 |
|---|---|---|---|
| D0: 기준선 | Codex | 상태·테스트·가용성 실측 | PARTIAL_READY/READY를 거짓 없이 구분 |
| D1: 순수 상태 기계 | Codex | `c3p_absence_mode.py`, 전용 테스트 | 트리거·상태 전이·종료 조건 단위 테스트 |
| D2: CLI 연결 | Codex | `csc.py` | `arm/status/stop`이 원문 상태를 보존하며 동작 |
| D3: 로컬 감시 연계 | Codex | `csc_swarm_watcher.py`, 전용 테스트 | 변화가 있을 때만 결과 카드 후보 생성, 유휴 모델 호출 0건 |
| D4: Antigravity 검토 | Antigravity | 읽기 전용 결과 카드 | 권한·중복·종료 조건 반례 제출 |
| D5: 최종 검증 | Codex | 전체 테스트·diff 감사 | 실제 `READY`에서 1회 유한 토론회 모의, P2 경계 확인 |

각 단계는 직전 단계의 테스트가 통과한 뒤에만 열린다. Antigravity에는 D4만 위임하며,
직접 코드 작성 권한을 부여하지 않는다.

## 10. 승인 게이트

이 문서는 연구·설계 산출물이다. D1 구현 전에 사용자 또는 Codex의 명시적 `IMPLEMENT` 지시,
그리고 `READY` 가용성 증거가 필요하다. 현재 `PARTIAL_READY`에서는 D0과 D4의 읽기 전용
작업만 허용된다.

## 11. 제안 전수정리와 정제 판정

| 사용자 제안 | 판정 | 정제 이유 |
|---|---|---|
| Codex가 토론회를 주도 | 채택 | 의제·종료·사용자 보고의 책임 주체를 하나로 유지한다. |
| Antigravity 중심 감시 | 조건부 채택 | 증거 수집 우선 배정은 가능하지만, 소켓 등록·하트비트가 모두 확인될 때만 실행한다. |
| 사용자가 부재 중 계속 대화 | 수정 | 대화의 지속성은 성과가 아니다. 변화 기반의 유한 토론회만 허용한다. |
| 가시적 결과물 의무 | 채택·축소 | 코드 diff를 강제하지 않는다. 결과 카드는 결정·구현준비·차단·행동없음 중 하나면 충분하다. |
| Claude Code 안전 역할 | 보류 | 현재 `quota_exhausted` 원문이 있어 회신을 기다리되 능동 호출·대체 표결은 금지한다. |
| Antigravity 구현 위임 | 단계화 | D4 읽기 전용 검토만 먼저 수행한다. D1~D3 코드는 `READY`와 Codex IMPLEMENT 승인 뒤에만 연다. |

### 채택하지 않는 주장

다음은 원문 증거가 없거나 현재 상태와 모순되어 설계에 넣지 않는다.

- `activate`가 항상 0ms에 자가치유하거나 Antigravity를 상시 생존시킨다는 주장
- Antigravity의 쿼터가 풍부하므로 Codex·Claude 사용량을 완벽히 보존한다는 주장
- `PARTIAL_READY`에서 실제 토론회 또는 3도구 합의가 열렸다는 주장

## 12. Antigravity 통보용 다음 작업 카드

**현재 단계: D4-PLAN-REFINE (읽기 전용).**

Antigravity는 아래 네 항목만 700자 이내로 제출한다.

1. `OFF/ARMED/RUNNING/PAUSED/종료` 전이표와 `READY`의 기계적 사전조건
2. 정확 트리거, 최대 메시지·시간·반복 횟수, 중복 종료 규칙
3. `c3p_absence_mode.py`, `csc.py`, `csc_swarm_watcher.py`의 최소 공개 API와 테스트 경계
4. P2, 가짜 READY, 직접 JSONL 기록, 권한 없는 파일 수정에 대한 수용 기준

금지: 코드·테스트·웹·Ollama·문서·큐 직접 수정, Claude Code 메시지 발송, 실제 토론회 시작.
수용 후에도 `READY` 및 Codex IMPLEMENT 지시가 없으면 다음 단계는 `PAUSED`다.
